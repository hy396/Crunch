# 补充方案：解除服务端英雄唯一性校验

## 背景

在上一方案《方案_英雄选择本地限制.md》中，我们把**UI灰显**限制在了本地玩家范围内。但在实施后发现：即使 UI 上没有灰显，点击别人已选的英雄仍然无法生效。

这是因为"禁止重复选择"的校验逻辑**不在 UI 层**，而是在**服务器端的 RPC 实现里**。

## 问题定位

真正的拦截点在 [MPlayerState.cpp:65-82](Source/Crunch/Private/Player/MPlayerState.cpp#L65-L82)：

```cpp
void AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation(const UPDA_CharacterDefinition* NewDefinition)
{
    // 安全检查
    if (!CGameState || !NewDefinition) return;
    
    // 如果角色已被其他玩家选择则退出
    if (CGameState->IsDefinitionSelected(NewDefinition)) return;   // ← 这里是拦截点
    
    // 如果玩家已有选择，先取消旧选择
    if (PlayerSelection.GetCharacterDefinition())
    {
        CGameState->SetCharacterDeselected(PlayerSelection.GetCharacterDefinition());
    }
    
    // 更新选择并通知游戏状态
    PlayerSelection.SetCharacterDefinition(NewDefinition);
    CGameState->SetCharacterSelected(this, NewDefinition);
}
```

客户端点击英雄时，调用链是：

```
CharacterEntryWidget 点击
    → ULobbyWidget::CharacterSelected
    → MPlayerState->Server_SetSelectedCharacterDefinition（Server RPC）
    → AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation（服务器端执行）
    → 命中 if (CGameState->IsDefinitionSelected(NewDefinition)) return;
    → 服务器直接返回，没有更新选择
    → 客户端没有收到任何同步回包，看起来就是"点击没反应"
```

因此即使我们把 UI 灰显去掉，服务器仍然会拒绝"已被选择"的英雄。

## 目标

允许多名玩家选择同一个英雄，让玩家在服务器端也能成功完成选择。

## 涉及文件

- `Source/Crunch/Private/Player/MPlayerState.cpp`
  - 函数 `AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation`（第 65~82 行附近）

## 修改方案

### 核心改动

将 `IsDefinitionSelected` 的检查和 `SetCharacterDeselected` / `SetCharacterSelected` 的调用移除或改造，使得"英雄唯一性"不再作为选择成功的前置条件。

**修改前：**

```cpp
void AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation(const UPDA_CharacterDefinition* NewDefinition)
{
    if (!CGameState || !NewDefinition) return;
    
    // 如果角色已被其他玩家选择则退出
    if (CGameState->IsDefinitionSelected(NewDefinition)) return;
    
    if (PlayerSelection.GetCharacterDefinition())
    {
        CGameState->SetCharacterDeselected(PlayerSelection.GetCharacterDefinition());
    }
    
    PlayerSelection.SetCharacterDefinition(NewDefinition);
    CGameState->SetCharacterSelected(this, NewDefinition);
}
```

**修改后：**

```cpp
void AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation(const UPDA_CharacterDefinition* NewDefinition)
{
    if (!CGameState || !NewDefinition) return;
    
    // 去除"唯一性"限制：多名玩家可以选择同一个英雄
    // 直接更新当前玩家的选择
    PlayerSelection.SetCharacterDefinition(NewDefinition);
}
```

关键点：
- 删除 `IsDefinitionSelected` 的早退判断
- 删除 `SetCharacterDeselected` 和 `SetCharacterSelected`（这两个函数是为了维护"已选英雄集合"的互斥状态，现在不需要了）
- 只保留 `PlayerSelection.SetCharacterDefinition(NewDefinition)`，它会通过 Replication 同步到各客户端

### 需要同步检查 CGameState 的相关接口

`CGameState` 可能有依赖"已选英雄集合"的地方，例如：

- `CanStartHeroSelection()` / `CanStartMatch()` — 判断可否进入下一阶段
- `IsDefinitionSelected` — 已被修改路径不再调用

建议查阅 `CGameState.h/cpp` 中这些函数的实现：

1. **如果 `CanStartMatch` 依赖"所有玩家选了不同英雄"**：需要改成"所有玩家都选了英雄（允许重复）"
2. **如果 `CanStartMatch` 只检查"所有玩家都选了英雄"**：不需要改动
3. **`SetCharacterSelected` / `SetCharacterDeselected` / `IsDefinitionSelected` 函数本身**：如果其他地方没有调用，可以保留不管（死代码）；想干净就一起删掉

## 可选的保守改法

如果担心改动影响范围太大，也可以**只删早退语句**，保留集合维护的调用：

```cpp
void AMPlayerState::Server_SetSelectedCharacterDefinition_Implementation(const UPDA_CharacterDefinition* NewDefinition)
{
    if (!CGameState || !NewDefinition) return;
    
    // 注释掉早退：允许重复选择
    // if (CGameState->IsDefinitionSelected(NewDefinition)) return;
    
    if (PlayerSelection.GetCharacterDefinition())
    {
        CGameState->SetCharacterDeselected(PlayerSelection.GetCharacterDefinition());
    }
    
    PlayerSelection.SetCharacterDefinition(NewDefinition);
    CGameState->SetCharacterSelected(this, NewDefinition);
}
```

**副作用**：`CGameState` 的"已选英雄集合"中会出现同一英雄被多次 `SetCharacterSelected`、但只被 `SetCharacterDeselected` 一次的情况，导致集合状态不准确。如果后续没有代码依赖这个集合，实际无影响；如果有依赖（比如 `CanStartMatch` 用它判断进度），则可能出现 bug。

**推荐：**如果确认 `CGameState` 集合不再被其他功能使用，直接用前面的"核心改动"方案清爽；如果不确定影响面，先用保守改法。

## 验证

修改后在 PIE 下启动 2~3 个客户端测试：

1. 客户端 A 选择英雄 X → A 的 PlayerState 显示英雄 X ✓
2. 客户端 B 也点击英雄 X → B 的 PlayerState 也更新为英雄 X（不再被拒绝）✓
3. 服务器端不报错、不掉线 ✓
4. 两位玩家都按准备后，对局能正常进入 ✓
5. 进入对局后，两名玩家各自生成所选英雄的角色 Pawn ✓（依赖 `CGameMode::SpawnDefaultPawnFor` 的角色生成逻辑，和英雄是否重复无关）

## 回滚

如果将来想恢复"英雄不能重复选择"的限制，只需恢复早退判断即可：

```cpp
if (CGameState->IsDefinitionSelected(NewDefinition)) return;
```

## 和前一方案的关系

| 方案 | 目的 | 位置 |
|------|------|------|
| 方案一（UI 灰显本地化） | 只有自己选的英雄显示灰色，其他玩家选择不会让英雄在本地变灰 | `LobbyWidget.cpp` 客户端 |
| 方案二（本文档） | 解除"英雄唯一"的服务端校验，允许多人选同一英雄 | `MPlayerState.cpp` 服务端 |

两个方案**必须配合使用**：
- 只改方案一 → UI 不灰了，但服务器拒绝，点了没反应

- 两个都改 → 完整实现"随便选"的功能
